# How StellarCade Works

StellarCade combines high-performance Soroban smart contracts with a cryptographic commit-reveal protocol to ensure fast, low-fee, and provably fair gameplay.

---

## The 3-Phase Round Lifecycle

```
[Phase 1: Commit] ────► [Phase 2: Execution] ────► [Phase 3: Reveal & Verify]
 Server publishes         Player inputs client       Server reveals seed;
 SHA-256(serverSeed)      seed & stakes on-chain     Client verifies offline
```

### Phase 1: Cryptographic Commitment
Before a match commences, the game server generates an unpredictable, high-entropy 256-bit secret string ($S$) and publishes its SHA-256 hash ($H$):
$$H = \text{SHA-256}(S)$$
Because SHA-256 is collision-resistant and preimage-resistant, the server is cryptographically locked into this secret and cannot alter it after observing the player's wager or choices.

### Phase 2: Player Input & On-Chain Settlement
The player selects their bet parameters:
- **Wager Amount**: Transferred non-custodially via a Soroban contract transaction.
- **Player Pick**: (e.g. Heads or Tails, Dice number, or Gauntlet path).
- **Client Seed ($C$)**: Generated by the player's browser or wallet (defaulting to a timestamped hash of their public key).

### Phase 3: Reveal & Offline Verification
Once the match concludes, the server reveals $S$. Both parties combine the entropy inputs in canonical order:
$$\text{Entropy Digest} = \text{SHA-256}(S \mathbin{\Vert} C \mathbin{\Vert} \text{nonce} \mathbin{\Vert} \text{ledgerHash})$$
The first 8 bytes (64 bits) of this digest are extracted as an unsigned big-endian integer ($V$), and the game outcome ($R$) is determined via modular reduction:
$$R = V \pmod{\text{rangeSize}}$$

For a 50/50 coinflip (`rangeSize = 2`):
- `R = 0` $\rightarrow$ **Heads**
- `R = 1` $\rightarrow$ **Tails**

## On-Chain Contract Roles & Architecture

StellarCade utilizes dedicated Soroban smart contracts written in Rust:

| Contract | Purpose | Audited Capabilities |
| :--- | :--- | :--- |
| **`coin-flip`** | Instant 1v1 duels & house matches | Escrows stakes, verifies client signatures, settles payouts |
| **`random-generator`** | On-chain verifiable randomness | Mixes protocol entropy, records verifiable commitments |
| **`prize-pool`** | Liquidity vault & jackpot distribution | Manages reserves, calculates yield splits, distributes prizes |
| **`achievement-badge`** | Soulbound Quest Tokens (SBTs) | Non-transferable on-chain XP tokens awarded for milestones |

---

## Audit Logs & Arbiter Dispute Resolution

In the rare event of network disconnection or dispute, every settled match writes an entry to a hash-chained audit log managed by the StellarCade Arbiter:
$$\text{Block}_n = \text{SHA-256}(\text{Block}_{n-1} \mathbin{\Vert} \text{MatchPayload})$$
This ensures that game outcomes cannot be pruned, rewritten, or selectively omitted after the fact.
